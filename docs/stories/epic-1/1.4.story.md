# Story 1.4: Basic Application Shell & Role-Based Routing

## Status

Done

## Story

**As an** OYSIPA User,
**I want** to see the main application layout and a navigation menu that is specific to my role,
**so that** I can only access the sections and features I am authorized to use.

## Acceptance Criteria

1.  Once logged in, a consistent application shell (e.g., with a header and side navigation bar) is displayed.
2.  The navigation menu dynamically displays links based on the user's role (e.g., a `Portal Administrator` sees a "User Management" link, while a `Staff` user does not).
3.  Users are prevented from accessing unauthorized pages by navigating directly to a URL.

## Tasks / Subtasks

- [x] **Frontend (oysipa-frontend)**
    - [x] Create a `Header` component (`src/components/Header.jsx`) that displays the application title and potentially user information.
    - [x] Create a `Sidebar` component (`src/components/Sidebar.jsx`) that will contain navigation links.
    - [x] Implement logic within `Sidebar.jsx` to dynamically render navigation links based on the logged-in user's role (obtained from the JWT).
    - [x] Modify `App.jsx` to include the `Header` and `Sidebar` components, creating the main application shell.

- [x] **Backend (oysipa-backend)**
    - [x] Create a middleware (`src/middleware/auth.js`) to verify JWTs and attach user information (including role) to the request object.
    - [x] Create a middleware (`src/middleware/authorize.js`) to check user roles against allowed roles for specific routes.
    - [x] Apply the `auth` middleware to all protected routes.
    - [x] Apply the `authorize` middleware to routes that require specific roles.

## Dev Notes

- **Role-Based Access Control (RBAC):** The JWT will contain the user's role. This role should be used on both the frontend (for UI rendering) and backend (for API access control).
- **Middleware:** Backend middleware is crucial for enforcing RBAC. The `auth` middleware should run first to verify the token, then the `authorize` middleware to check roles.
- **Frontend Navigation:** The `Sidebar` component should read the user's role from the stored JWT (or a global state derived from it) to decide which links to display.

## Testing Guidance

- **Unit Tests:**
    - Backend: Test `auth` middleware to ensure it correctly verifies JWTs and attaches user info. Test `authorize` middleware to ensure it correctly grants/denies access based on roles.
    - Frontend: Test `Sidebar` component to ensure it renders correct links for different mock user roles.
- **Integration Tests:**
    - Attempt to access a role-restricted backend API endpoint with an unauthorized user's token; verify a 403 Forbidden response.
    - Attempt to access a role-restricted backend API endpoint with an authorized user's token; verify a 200 OK response.
- **End-to-End (E2E) Tests:**
    - Log in as a `Director-General` user: Verify all navigation links are visible. Attempt to navigate to a `Portal Administrator`-only page (if one exists); verify access is granted.
    - Log in as a `Portal Administrator` user: Verify specific navigation links (e.g., "User Management") are visible, while `Director-General`-only links are hidden. Attempt to navigate to a `Director-General`-only page; verify redirection or access denied.
    - Log in as a `Staff` user: Verify only `Staff`-relevant navigation links are visible. Attempt to navigate to `Portal Administrator` or `Director-General`-only pages; verify redirection or access denied.
    - Verify that direct URL navigation to unauthorized frontend routes results in redirection to the login page or an access denied message.
